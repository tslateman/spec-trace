The Gap

Requirements and code live in different worlds

Requirements

Confluence, Notion, Google Docs

Siloed. Stale. Disconnected.

✗
Tests

pytest, CI pipelines

No link to what they verify.

When requirements change, how do you know which tests to run?
When tests fail, which requirements are affected?
You don't.

Presenter Notes

This is the core problem SpecTrace solves. Requirements live in docs, tests live in code, and there's no automated connection between them. Teams manually track coverage in spreadsheets, which go stale immediately.

Presenter Notes

Requirements are markdown files in your repo. Tests use a pytest marker to declare which requirement they verify. SpecTrace parses both and builds the traceability automatically.

Presenter Notes

Some verifications can't be a single test — they're multi-step processes. Flows let you define pipelines where each step must pass before the next runs. Great for integration testing and E2E flows.

6

Impact Analysis

Know which tests to run when specs change

# Which tests are affected by changes in this PR?
$ spectrace impact main feature-branch

Changed specs:
  specs/auth/REQ-AUTH-001.md
  specs/auth/REQ-AUTH-002.md

Affected tests (8 total):
  tests/test_login.py::test_login_success
  tests/test_login.py::test_login_invalid_password
  tests/test_login.py::test_login_locked_account
  tests/test_password.py::test_reset_email_sent
  ...

Run these tests before merging:
$ pytest tests/test_login.py tests/test_password.py
  • Git-aware — Compares any two refs (branches, commits, tags)
  • Hierarchy expansion — Changes to parent specs affect child requirements
  • CI integration — Exit code 1 if tests are affected
Open Impact Analysis →
Presenter Notes

When specs change, you need to know what to re-test. Impact analysis traces the changes through the requirement graph to find all affected tests. Use it in CI to gate merges or trigger targeted test runs.
